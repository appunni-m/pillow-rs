# pillow-rs benchmark evidence

This page is a landing page for the maintained benchmark contract. It replaces
the old six-target table, which was generated by a retired harness and no
longer described the active manifest. Current numbers are published only with
their run identity and correctness evidence.

## Active benchmark contract

The manifest currently indexes 744 standard workloads. Each workload records
its input case or workflow, target subjects, build profile, mode and dimensions,
cache state, measurement boundary, warmup, iterations, samples, metrics, and
correctness gate. The standard repeat policy is 5 warmup iterations, 20
measurement iterations, 5 samples, and one concurrent worker (100 timed
executions).

Use the maintained targets:

```sh
MIGRATION_BENCHMARK_PROFILE=quick make migration-parity-benchmark
MIGRATION_BENCHMARK_PROFILE=standard make migration-parity-benchmark
make migration-parity-pipeline-report
```

The JSON output under `build/migration-parity/` is the evidence record. A
benchmark comparison is valid only when both sides have compatible manifest and
input hashes, runtime identity, requested/actual backend, terminal receipts, and
the same measurement policy.

## What the numbers do and do not mean

- A parity pass proves observable output for that input; it does not prove a
  native GPU path executed.
- A `python-gpu` row with a host-control receipt is routing evidence. It is not a
  native GPU timing claim.
- Setup, pipeline, and terminal/readback phases are kept separate. A process
  timing must not be presented as an operation timing.
- Medians and spread are reported with the machine, toolchain, commit, and
  policy. A single local timing is not a universal speedup.
- Profiler-instrumented runs are diagnostic and are excluded from acceptance
  samples.
