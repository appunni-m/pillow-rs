# RGB GetBBox blank-image CPU optimization

## Decision

Keep the serial-CPU RGB precheck optimization that tests the first pixel as
before, then scans the remaining bytes as 8-byte groups. It preserves the
early return for dense images and cuts the blank-image scan cost by about 8×
on ARM64. The code is in `pillow-rs/src/ops/analysis.rs`.

The earlier suggestion to remove the precheck was based on a false premise:
`if !raw.iter().any(...) { return Ok(None); }` prevents the row scan on blank
images. Removing it selects a slower per-pixel scan. A first word-scan
variant did make blank input much faster, but its dense guards were sensitive
to host drift. The retained variant scans the first RGB pixel with the
original fast exit, then applies word grouping to the rest.

This is an ARM64 serial-CPU result for one new RGB workload. x86_64, SIMD,
GPU, Parallel CPU, and other GetBBox modes remain open. The dense and noise
CPU cases still fall short of the long-term 2× Pillow target.

## Workloads and protocol

- Blank primary: `pil-image-image.getbbox.materialized.rgb-blank-1024x768`
- Full-width guard: `pil-image-image.getbbox.materialized.rgb-filled-1024x768`
- Dense-data guard: `pil-image-image.getbbox.materialized.rgb-noise-1024x768`
- Exact parity cases: corresponding `PIL.Image.Image.getbbox.nuanced.performance-rgb-*-1024x768` cases.
- Warm direct `call` boundary on an already materialized RGB image; 5 warmups, 20 iterations × 5 samples, concurrency 1.
- macOS 15.7.7 ARM64, CPython 3.12.13, Pillow 12.2.0.
- Every reported target execution requested and reported `cpu`, with one completed GetBBox and no fallback.
- The blank case's `raw[3..]` length exercises the 5-byte tail after 8-byte grouping.

The accepted variant uses the A2–B3–B4–A3 bracket. All four legs passed exact
parity for all three selected cases (B4 reused B3 parity only after the report
and target identity matched). Controls used the same loaded core hash
`93e393bdcb9c3caa86bc188aa521a81b92b28729a1f8258a4af073062a6bd390`; both
candidate legs used `6797daf45dbdc1d8071caead12c0e96c0bf6138c308241de716e7bf135bf54fc`.
The final rebuilt extension matched the candidate hash exactly.

## A2–B3–B4–A3 results

Times are per-call medians in milliseconds. `Pillow / CPU` is the same-report
Pillow latency divided by serial-CPU latency.

| Leg | Workload | Pillow | CPU | Pillow / CPU |
| --- | --- | ---: | ---: | ---: |
| A2 control | blank RGB | 0.233333 | 0.663938 | 0.351× |
| B3 candidate | blank RGB | 0.222270 | 0.081666 | 2.722× |
| B4 candidate | blank RGB | 0.221916 | 0.081792 | 2.713× |
| A3 control | blank RGB | 0.227125 | 0.654521 | 0.347× |
| A2 control | filled RGB | 0.003000 | 0.001875 | 1.600× |
| B3 candidate | filled RGB | 0.002250 | 0.001458 | 1.543× |
| B4 candidate | filled RGB | 0.002292 | 0.001500 | 1.528× |
| A3 control | filled RGB | 0.002292 | 0.001563 | 1.467× |
| A2 control | noise RGB | 0.006250 | 0.002250 | 2.778× |
| B3 candidate | noise RGB | 0.002666 | 0.001583 | 1.684× |
| B4 candidate | noise RGB | 0.002708 | 0.001583 | 1.711× |
| A3 control | noise RGB | 0.002750 | 0.001750 | 1.571× |

Mean control latency for the blank workload was 0.659230 ms; mean candidate
latency was 0.081729 ms, an 8.07× reduction. The same-report CPU speedups over
Pillow were 2.71–2.72× in both candidate legs. Filled-image CPU latency was
not slower than its control bracket. The noise target was also below both
control medians; its Pillow timing varied sharply between A2 and A3, so the
same-report noise ratios are retained as observations rather than treated as
a stable improvement.

## Generated baseline admission

The B3 benchmark, parity result, exact benchmark/parity input JSON artifacts,
and their selected comparison evidence are imported into the local generated
PerfDB. Strict baseline promotion was attempted and rejected because these
benchmark reports do not declare `environment.runner_id`; the importer marks
the machine-derived identity unresolved. The baseline channel also requires a
validated `workflow-parity-link@2` cross-run proof with its producer and
source-build receipts. No identity or proof fields were inferred or filled in
after measurement, and no baseline was promoted. A later run that supplies the
stable runner ID and complete admitted proof package can promote this selected
workload without rerunning unrelated cases.

Each A/B leg retains a benchmark result, parity result, benchmark and parity
attestations, and raw samples under `A1/` through `A3/` and `B1/` through
`B4/`. B1/B2 are the superseded first word-scan variant; A1/B1/B2/A2 records
why the first-pixel fast exit was restored before measuring B3/B4.

The new blank parity case and workload are generated by
`scripts/build_migration_parity_inputs.py` and indexed in the existing public
fixture files. No full benchmark or coverage campaign was run. The x86 host's
single existing checkout was inspected read-only; this experiment used no
remote project or target copy.
