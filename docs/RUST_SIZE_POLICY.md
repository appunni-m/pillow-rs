# Rust size policy and legacy inventory

This contributor policy defines the file and function size ratchet used by
make checkstyle. The machine-readable ceilings and per-function signatures
live in [scripts/rust_size_baseline.json](../scripts/rust_size_baseline.json).

## Limits

| Measure | Review signal | Hard ceiling |
| --- | ---: | ---: |
| First-party Rust source file | 800 physical lines and above | 1,000 physical lines |
| Rust function or method body | Clippy too_many_lines threshold: 60 | 100 counted body lines |

The checker rejects a new file over 1,000 lines, a new function over 100 counted
body lines, and growth beyond an existing legacy ceiling. Legacy entries may
only shrink. After a verified reduction, run
make checkstyle-update-baseline, inspect the full baseline diff, and remove the
corresponding ownership row once the file and all over-limit functions in
that path have left the baseline.

## Scope and exclusions

The file scanner follows the current Cargo workspace members:
pillow-rs/, pillow-rs-py/, and pillow-rs-js/. It recursively includes
first-party .rs files in source, unit and integration tests, examples,
benches, and build scripts. When a workspace member is added or removed, update
the scanner's package list and this scope description in the same change.

The scanner excludes a source only when one of its path components exactly
matches .git, target, vendor, node_modules, or generated. These component
exclusions cover repository metadata, compiler output, vendored or dependency
code, and explicitly generated sources. There is no generic
build-directory exclusion; maintained Rust source under a workspace member
is counted unless it is under one of the listed components. Build output
outside the workspace package roots is outside the scan.

File length is the number of physical lines returned by Python splitlines
for the UTF-8 source file. Every physical line counts, including blank lines,
comments, documentation comments, attributes, macro invocations, and tests.
A final newline does not add an extra empty line.

## Function counting rules

The function gate consumes Clippy's clippy::too_many_lines diagnostics from
cargo clippy --workspace --all-targets --all-features using the pinned
toolchain in rust-toolchain.toml. It uses Clippy source spans, not a regular
expression over Rust syntax. clippy.toml sets the review threshold to 60;
scripts/run_clippy_quality.py applies the 100-line hard ceiling and compares
over-limit functions against the recorded baseline.

Clippy counts nonblank, non-comment-only lines in the function body source
span. For block bodies, the outer braces are removed and leading or trailing
blank space is trimmed. A code line with a trailing comment still counts once;
a comment-only line does not. The function signature and attributes attached
outside the body span do not count. Attributes inside a body and macro
invocation source lines count as code. Expanded macro text is not counted as
separate source lines, and functions generated by an external macro expansion
are skipped by this lint. Closures are not linted as separate functions; their
source lines remain within the enclosing function body. A nested function is
counted within the enclosing body's source span and is also checked as its own
function.

The inventory reflects the configured toolchain and host build target.
--all-targets --all-features includes workspace tests and feature combinations
for that build; it does not compile every architecture. Recheck the counting
description when the Rust toolchain or Clippy implementation changes. See the
[Clippy lint documentation](https://rust-lang.github.io/rust-clippy/master/index.html#too_many_lines)
and its [implementation](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/functions/too_many_lines.rs).

## Baseline and exception maintenance

scripts/rust_size_baseline.json records:
- file_lines: the recorded ceiling for each legacy file over 1,000 lines;
- function_lines: each legacy function's path, normalized signature,
  occurrence, and recorded line ceiling;
- legacy_owners: one owner, reduction task, and reason for each path that has
  either a legacy file or function entry.

All current exceptions predate the size ratchet and have an owner plus an open
focused Kata reduction task. New over-limit files or functions are failures;
they must not be added as ordinary baseline debt. A reviewed exception, if a
maintainer approves one, needs a specific reason, an owner, and a reduction
task, and must remain visible in the baseline inventory. The incremental
checkstyle gate tracked by Kata pillow-rs#q730 should validate that the
ownership map covers every active legacy path and has no retired entries.

make checkstyle-update-baseline rewrites the file and function ceiling
sections from current measurements, preserves metadata for active paths, and
removes owner entries for retired paths. It fails if an active path has no
owner, reason, or qualified reduction task; add that metadata before recording
a new exception. Review the function signatures, file ceilings, legacy_owners,
and this document together after each baseline change. Do not add
#[allow(clippy::too_many_lines)] or raise thresholds to make a failing change
pass.
