# Pillow Compatibility Program

Status: active  
Created: 2026-07-24  
Authority: this document is the canonical plan for Pillow image API parity
outside the FreeType-specific parity program.

## Goal

Deliver exact Pillow compatibility from one pure-Rust implementation through
all three supported surfaces:

1. the Rust API;
2. the Python ABI;
3. the JavaScript/WASM ABI.

Compatibility is trusted only when a version-pinned Pillow oracle produced the
expected result and a Coverage MCP managed run produced a valid, freshly
ingested coverage snapshot. A passing test without executed-code coverage is
not accepted as proof. Unit tests may remain useful during development, but
their results do not count toward compatibility completion.

## Non-Negotiable Architecture

### Rust owns behavior

All image semantics, algorithms, validation, error selection, image-mode
handling, drawing, compositing, filtering, pipeline behavior, and
format-independent data conversion must be implemented in Rust.

The Python and JavaScript layers may only:

- convert host-language values to Rust values;
- validate host object identity or type where the ABI requires it;
- select an overload based on host-language type;
- delegate to Rust;
- convert Rust values and errors back to the host ABI;
- read or write files before passing bytes to Rust codecs.

They must not contain algorithmic loops, pixel processing, image mathematics,
filesystem orchestration, subprocesses, temporary-file workflows, fixture
interpretation, or alternate implementations of Rust behavior.

### Core and codec boundary

Filesystem paths and host objects do not belong in `pillow-rs` core. Bindings
or applications read and write files; Rust codec APIs consume and produce
bytes.

The codec layer owns:

- magic/signature detection and format selection;
- header parsing, dimensions, sample depth, channel mode, and safety limits;
- compressed pixel decoding and encoding;
- palette, indexed-pixel, transparency, and alpha semantics;
- format-required color/sample conversion;
- EXIF, ICC, XMP, DPI, orientation, and container metadata extraction and
  preservation;
- multiframe and animation frames, offsets, duration, loop, disposal, and
  blending;
- encoding options and format-specific validation;
- truncated/corrupt input detection and Pillow-compatible errors;
- JPEG progressive, DCT/Huffman, subsampling, and CMYK behavior;
- PNG filters, compression, interlacing, indexed color, and `tRNS`;
- GIF palette, transparency, animation, and disposal behavior;
- TIFF endianness, sample layout, strips/tiles, and multipage behavior;
- the corresponding format-specific behavior for BMP, WebP, ICO, and AVIF.

Generic resize, paste, drawing, compositing, filters, and effects belong in
the image/compute core rather than an encoder or decoder.

## Test Trust Model

### The only compatibility oracle

Expected compatibility results must be generated by the pinned Pillow oracle.
Tests must compare the public result exactly:

- image mode;
- dimensions;
- complete pixel bytes;
- palette bytes and metadata where applicable;
- exact scalar and container type;
- exact value;
- exact exception type and message;
- mutation and object-lifetime behavior;
- encoded bytes when the format is deterministic;
- decoded pixels and metadata when encoded bytes legitimately vary.

Mocks, monkeypatches, hard-coded replacement results, binding-side
reimplementations, tolerance added to hide a mismatch, and expected-output
editing are forbidden. A test must call the real public Rust, Python ABI, or
JavaScript ABI surface being claimed.

Lossy codecs and inherently nondeterministic APIs require an explicit,
documented oracle contract. They must never silently fall back to a weaker
hash, tolerance, descriptor-only, or type-only assertion.

### Coverage MCP is the evidence ledger

All accepted compatibility runs must:

1. use an immutable, human-approved Coverage MCP registration;
2. run through the Coverage MCP ledger;
3. declare a real coverage artifact;
4. finish with successful automatic coverage ingestion;
5. retain the resulting snapshot ID;
6. report line, branch, function, and region coverage where the report format
   supports them;
7. query uncovered code and use it to drive the next independent oracle input;
8. compare against a lineage-compatible baseline before claiming progress.

The Coverage MCP state inspected on 2026-07-24 had 40 managed runs and four
approved commands, but **zero coverage snapshots**. The existing
`fixture-coverage-check` validates manifest-to-fixture mapping; it does not
prove that implementation lines, functions, or branches executed. Existing
pass counts therefore remain diagnostic history, not accepted compatibility
coverage.

The Coverage MCP dashboard is available at <http://localhost:59471/>.

### Inputs represent independent paths

The fixture corpus must be redesigned around independent behavioral paths,
not case-count growth.

Every retained input must have a documented reason, such as:

- it executes a previously uncovered line, branch, function, or region;
- it selects a different image mode or storage representation;
- it selects a different argument-validation or error-ordering path;
- it exercises a boundary value or size transition;
- it changes transparency, palette, alpha, clipping, or mask behavior;
- it crosses a codec format, bit-depth, metadata, frame, or corruption path;
- it selects a distinct compute backend or pipeline transition;
- it proves ABI-specific coercion, lifetime, mutation, or return-type behavior.

Inputs are duplicates when they execute the same relevant implementation path
and assert the same semantic contract without adding a boundary, mode, ABI, or
error distinction. Duplicate inputs must be removed only after Coverage MCP
shows that their removal does not reduce relevant line, branch, function, or
region coverage.

Coverage is a discovery tool, not the only selection criterion: two inputs can
hit the same lines while proving different public values, types, modes,
overflow behavior, or error ordering. Those semantic distinctions must be
retained and documented.

### One oracle corpus, three consumers

The same canonical oracle case must be consumable by:

- a Rust integration harness calling the public Rust API;
- a Python integration harness importing and calling the installed PyO3 ABI;
- a JavaScript integration harness calling the built WASM ABI in Node and,
  for browser-specific behavior, a browser harness.

Each surface must report executed case IDs and explicit unsupported cases.
Skipped or absent cases are gaps, not passes. Surface-specific inputs are
allowed only for genuine ABI contracts and must link back to the same
operation/behavior inventory.

The harness must verify that all three surfaces agree with the Pillow oracle,
not merely that Python and JavaScript agree with Rust.

## Verified Findings

### Python is not yet a thin client

`scripts/check_bindings.py` currently reports 60 binding-layer violations
across:

- `pillow-rs-py/python/pillow_rs/image.py`;
- `imagedraw.py`;
- `imagefilter.py`;
- `imagefont.py`;
- `imageops.py`;
- `operations.py`.

The checker emits warnings and still succeeds, so CI does not enforce the
non-negotiable boundary. Loops, arithmetic, complex branching, and
orchestration remain in Python.

`pillow-rs/src/image.rs` also exposes path-based `open` and `save` behavior and
performs filesystem I/O. This violates the core boundary. Binding layers must
read/write bytes and delegate byte decoding/encoding to Rust.

### Current parity is not fixture-only

The last inspected managed Python run contained 1,677 tests:

- 1,593 generated fixture parity cases;
- 41 PA mutation/public API cases;
- 38 direct `putdata` cases;
- 5 fixture integrity/meta cases.

It passed 1,659 and failed 18: 14 `effect_spread` cases and four `getim`
cases. Separate historical managed runs reported 22/22 backend parity and
79/79 Rust core tests. These counts do not include ingested implementation
coverage and therefore are not completion evidence.

The useful mutation, coercion, error-ordering, registry-integrity, and
anti-mocking contracts must be represented in the redesigned oracle corpus
rather than trusted as unrelated unit tests.

### Codec integration is incomplete

The adjacent codec implementation already separates JPEG, PNG, GIF, BMP,
TIFF, WebP, ICO, and AVIF decode/encode/inspection modules and exposes
byte-oriented decode, encode, sequence, inspection, and format detection.

The image API does not yet fully expose this capability:

- `get_child_images()` does not provide decoded sequences;
- `getexif()` and `getxmp()` are effectively empty;
- complete codec encoding options are not exposed through image save APIs;
- metadata and multiframe behavior are not fully connected;
- path I/O is incorrectly located in image core.

EXIF extraction belongs to the codec; applying EXIF orientation remains a
generic image operation.

### CPU and SIMD coverage is incomplete

The backend registry contains:

- 86 CPU-supported `PipelineOp` operations;
- 69 SIMD-pool-supported operations;
- 17 CPU operations without SIMD registration.

The missing SIMD registrations are:

- `Color3DLut`;
- `DrawArc`;
- `DrawChord`;
- `DrawCircle`;
- `DrawEllipse`;
- `DrawLine`;
- `DrawPieslice`;
- `DrawPoint`;
- `DrawPolygon`;
- `DrawRectangle`;
- `DrawRoundedRect`;
- `EffectMandelbrot`;
- `EffectNoise`;
- `EffectSpread`;
- `ExtractBand`;
- `LinearGradient`;
- `RadialGradient`.

Registered SIMD support is not equivalent to hand-vectorized SIMD. The
current x86 and ARM modules delegate to scalar implementations. The SIMD pool
therefore supports 69 operations structurally, while explicit
architecture-intrinsic coverage is effectively zero. Future reporting must
distinguish:

1. CPU semantic support;
2. SIMD-pool registration;
3. compiler auto-vectorization;
4. verified architecture-specific vectorization;
5. exact Pillow parity for every backend.

### GPU batches retain pixels but over-dispatch

When every operation is GPU-supported, the current pipeline:

- uploads the source once;
- retains intermediate images in GPU ping-pong buffers;
- avoids intermediate CPU readback;
- reads the final result back once.

It is not a single optimized GPU submission. Each operation creates a command
encoder and compute pass, submits separately, and performs a blocking
`device.poll(Maintain::Wait)`. A pipeline of `N` operations therefore incurs
approximately `N` submissions and `N` waits plus final readback. A global GPU
execution mutex serializes complete batches, and readback allocates fresh
staging resources.

Routing also requires one backend to support the entire pipeline:

- automatic routing moves the whole pipeline to SIMD/CPU when any operation is
  unsupported by GPU;
- explicit GPU routing returns an error;
- no GPU-to-CPU-to-GPU partitioning or cost-aware bridge exists.

The pipeline avoids repeated copyback for fully supported chains, but loses
GPU acceleration for supported portions of mixed chains.

### Existing documentation can be stale

Historical documents contain superseded counts and completed-gap claims, such
as assertions that Python binding violations were eliminated or that SIMD had
zero registrations. Registry inspection and managed evidence must be used
instead of copying historical status. When a milestone changes a count, this
document must be updated in the same commit.

## Acceptance Gates

An operation is complete only when all applicable gates pass:

- [ ] The behavior is implemented once in pure Rust.
- [ ] Python contains delegation and ABI conversion only.
- [ ] JavaScript contains delegation and ABI conversion only.
- [ ] The case expected value was generated by the pinned Pillow oracle.
- [ ] Exact result, mutation, type, and error semantics are asserted.
- [ ] The canonical case runs through the Rust public API.
- [ ] The same case runs through the installed Python ABI.
- [ ] The same case runs through the built JavaScript/WASM ABI.
- [ ] No surface silently skips or substitutes the operation.
- [ ] CPU output exactly matches Pillow where CPU applies.
- [ ] SIMD output exactly matches Pillow where SIMD applies.
- [ ] GPU output exactly matches Pillow where GPU applies.
- [ ] Coverage MCP ingested fresh coverage artifacts for the relevant
      Rust/Python/JS suites.
- [ ] Coverage queries show the intended lines, branches, functions, and
      regions executed.
- [ ] Removing duplicate cases did not reduce coverage or semantic-path
      inventory.
- [ ] Relevant format, mode, metadata, multiframe, and error cases are covered.
- [ ] No fixture, expected output, tolerance, threshold, mock, or host-language
      workaround hides a mismatch.
